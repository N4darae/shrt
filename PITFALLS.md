# PITFALLS

Symptom → cause → fix. Every entry is something that actually happened in the repo shrt was
developed in, with the pointer that lets you re-check it.

**Read the receipts as history, not as instructions.** The mechanism in each entry is a property of
shrt and travels to any repo; the particulars are not. Host names, app codes, migration numbers,
`errmsg.*` call sites and counts of things belong to the backend this file grew up against, and in
a repo that copied this folder they are evidence of how the pitfall was found, not a command to
run. Where an entry gives a command to re-derive a number, that command is the part to keep.

---

## 1. A key you invented was accepted and did nothing

**Symptom.** `shrt chain lint` says `ok`, the run passes, and the step never tested what you meant.

**Cause.** Until 2026-09-11 all three loaders used plain `yaml.Unmarshal`, which drops keys the
struct does not declare. `allow_failure:` (real key: `allow_fail:`) made a step silently *required*
to pass; `one_of:` made an expectation assert **nothing** while still reading as checked; a config
typed `host_overide:` would have sent every request with the wrong SNI and `Host`.

**Fix.** Loaders now decode with `KnownFields(true)` and reject the file. The habit that outlives
the fix: **look the key up in `GRAMMAR.md` rather than writing the one another tool would use.**
`{chain,contract,config}/unknownfield_test.go` in the shrt module pin it.

## 2. A green chain that proves nothing, because the descriptor is stale

**Symptom.** An assertion on a field that is plainly in the response reads as "the field is
missing", so you "fix" the chain.

**Cause.** A response whose message the descriptor does not know is kept **raw** — camelCase, zero
values omitted. Lint cannot catch this: lint validates against whatever the descriptor says, so a
stale descriptor is self-consistent.

**Fix.** `shrt catalog build` after any proto change. `shrt doctor` rebuilds the descriptor and
fails when the bytes differ from the one on disk. (In the development repo the same comparison is
`scripts/check-descriptor-fresh.sh`, run by its `scripts/check.sh`; recorded there at commit
`4251e77`.)

## 3. `not_empty` used where `exists` was meant

**Symptom.** A step goes red against a perfectly good response, or green against an empty one.

**Cause.** `not_empty` is false for `""`, `0`, `false`, `[]` and `{}`. On a count field it asserts
"non-zero", not "present"; on a list it asserts "has rows". `0` is zero by the field's proto type, so
an int64 stored as the string `"0"` is as empty as an int32 `0` (until 2026-09-24 it passed).

**Fix.** `GRAMMAR.md` §1 prints the evaluated truth table — it is generated by running the rules,
not by describing them. Use `exists: true` for presence, and read entry 26 first: presence means
less than it looks like on a proto3 scalar.

## 4. A run that says `error`, read as a backend failure

**Symptom.** A chain goes red and the report blames an rpc.

**Cause.** `error` is the third run status, and nearly always it means **no request was sent for
that step**: a reference or an auth body would not resolve, or the login failed. Then nothing
reached the backend, so it says nothing about the backend. It is usually an unset env var or a
`${...}` naming something the chain never created. The rarer cases where the request did go out
are a transport failure after sending, an answer that is not JSON, and a per-item verdict path that
cannot be read; the step's `error` line says which.

**Fix.** Read the status word before the step name. `failed` is evidence about the server; `error`
is almost always evidence about the fixture, and its `error` line tells you when it is not.

One case used to break that rule and no longer does: with `conventions.validate_output: true`, a
response the descriptor cannot read was reported as `error` although the request had been sent and
answered. It is now `failed` with `"drift": true` on the step — a third reading, and the one the
status words could not express. See entry 29.

## 5. A cached, still-valid token that shrt refuses to use

**Symptom.** A token in `.shrt/tokens.json` has not expired, yet `shrt run` exits 1 before sending
anything, with no run record: `step "<id>" (step 1) runs under auth profile "<profile>", whose login
body reads ${env.API_PASSWORD}, and env API_PASSWORD is not set, so nothing was sent`.

**Cause.** Deliberate, not a bug: the cache key is a hash of the target (`target.base_url`, and
`host_override` when set), the login procedure **and the resolved request body**, so a token minted
for one credential is never handed to another, and a token one backend issued is never sent to a
different one after `base_url` changes. Resolving the body is therefore a precondition of *reading* the cache,
and an unresolvable body returns an empty key — a miss.

**Fix.** Supply the credential. There is no path that runs a chain from the cache alone, by design.

## 6. A contract citation that rots

**Symptom.** A `source:` entry names a file nobody can find, and the reader concludes they have
misunderstood rather than that the note is stale.

**Cause.** Two flavours, both measured on 2026-09-11. Four entries named
`db/migration/000037_create_movement_fee.up.sql`, a file that never existed — the *number* was
right and the *name* was written from memory. And `:line-range` suffixes across the overlays drift
every time a file is split, which is why the parent repo's own rule is to anchor on function names.

**Fix.** Resolve every `source:` path before committing it — strip the `:line-range` first. Anchor
prose on names, not line numbers. Re-derive with this, run from your repo root — the directory
that holds `.shrt/` — since `source:` paths are relative to it:

```bash
python3 - <<'EOF'
import yaml, glob, os, re
for p in glob.glob('.shrt/contracts/*.yaml'):
    d = yaml.safe_load(open(p))
    for rpc, spec in (d.get('rpcs') or {}).items():
        for f in (spec.get('source') or []):
            path = re.sub(r':[0-9,\-]+$', '', f.strip())
            if not os.path.exists(path):
                print(os.path.basename(p), rpc.split('/')[-1], f)
EOF
```

## 7. A failure code the contract never knew about

**Symptom.** Coverage looks complete; a code the backend raises is outside the denominator
entirely, so nothing ever asks whether it fires.

**Cause.** The contract is hand-maintained and the backend is not. On 2026-09-11 two of 193 codes
were declared nowhere — and one of them, `1313`, was raised by a file the contract *already listed
in that rpc's own `source:`*. Both have since been declared: the same scan read 0 undeclared, out
of the same 193 distinct codes, on 2026-09-12.

**Fix.** Cross-check the two sides mechanically rather than by reading. `errmsg.New` calls span
several lines, so a line-oriented regex matches nothing — scan the file as one string and take the
first `<digits>, "<Reason>"` after each `errmsg.New`. Compare against every `failures:` entry, both
the per-rpc blocks and the domain-level one. Do not quote either number from here.

Compare the codes your backend actually raises against the codes your contracts declare. shrt ships
no tool for that — the comparison needs a reader of YOUR backend's error constructor — so it is a
script you write once and run in your own gate. The shrt repository has one for its own backend
(`scripts/contract-quality.py`), kept as a worked shape rather than something you can run here.

Declared is not the same as reached, so then check the branch is reachable from a chain at all:
every chain calling `FetchDealMarginList` sent `SIGN_FLAG_UNSPECIFIED`, the one value that skips the
guard, so the branch had never been entered by anything until a chain was written for it on
2026-09-11. Re-derive the chain count before quoting one; it moved the same day this was written.

## 8. An alias that quietly wires both legs to one id

**Symptom.** A deal is rejected for using the same asset twice, or two "independent" entities turn
out to be one.

**Cause.** `<rpc>@<alias>->path` asks for an independent instance, but an alias the target never
declares creates a second *identical* step. Lint warns, because it is nearly always a typo rather
than a deliberate duplicate.

**Fix.** Declare the alias on the target with the fields that make it different
(`aliases.<name>.fields`), and read the `# order:` line from `plan`.

## 9. `from` where `same_as` was needed

**Symptom.** A field stays permanently unfilled and no `from` can reach it.

**Cause.** `from` reads a **response** path. Some values never appear in any response —
`AssignStaffRole` keys on `username` while `CreateStaffResponse` returns only
`id_staff_principal`. Three contract authors hit this on five fields before `same_as` existed.

**Fix.** `same_as: <rpc>->request_path` reads what the producer was **called with**. Lint rejects a
response-only field there with "not a REQUEST field", because naming one means you wanted `from`.
At plan time both sites are rewritten onto one generated var, so they cannot drift apart — and that
drift is silent, because the server answers `OK` and finds nothing.

## 10. A drift test that poisons the baseline

**Symptom.** The next replay of a safe spot reports a regression nobody caused.

**Cause.** Some vars reach shared state. On `seed-position-exposure`, `-var rate=` writes into the
USD/VND pair every chain shares, and the freeze takes the latest rate in its window — so a one-off
`rate=26000` is picked up by the next replay and read as a backend change. `quantity` is safe
because the movement lands in a book the tag makes fresh.

**Fix.** Before perturbing a var to test the differ, ask what else reads it. Perturb something the
chain's own tag isolates.

## 11. An expect-fail chain that passes

**Symptom.** The development repo's `verify-all-flows.sh` sweep reports `UNEXPECTED … got=PASSED want=FAILED`.

**Cause.** This is the sweep working. Such a chain asserts a **pre-fix defect**; it must FAIL. A
PASS means the fix that made it fail has fallen off the target — a deploy regression, not a chain
bug.

**Fix.** Check which build the target is actually running before touching the chain. Never "fix"
one of these chains to make the sweep green. A run record answers that question only if it was
stamped: set `target.build_header` if the server reports its version in a header, or pass
`shrt run -build <label>`, and compare `build` across the records before comparing verdicts.

## 12. A plan that lints, runs, and means nothing

**Symptom.** A composed chain is green end to end and reproduces a state no operator would ever
create.

**Cause.** `plan` wires ids the contracts say to wire. It has no idea that a movement in one asset
should not discharge an obligation in another.

**Fix.** Read the `# order:` line as a claim about the business flow and check it against the domain
description in the overlay. This is the one part of composition that is not mechanical.

**The narrower version of this — a planned body nobody filled in — lint does catch**, per step and
per field: `sends an empty string or a placeholder enum for <fields>, and the contract does not say
that is deliberate`. It is a WARNING, and it is silenced three ways, all of them correct: name the
field in the contract's `required:`, where the stronger error already covers it; give the field a
`from`, `same_as` or `value` in the contract; or answer that field's `note:` TODO to say the empty
value is the point (`fetch_..._unfiltered` steps in the development repo do exactly that). A step
that asserts a refusal is not checked at all. On a fully curated corpus it fires on nothing, which is the intended end state
rather than evidence the check is inert.

**Read its scope precisely, because two neighbours look identical and are not reported:**

- **A numeric zero is NOT reported.** `amount_minor: "0"` from a scaffold and a deliberate limit of
  zero are the same bytes, and §3 of `PLAYBOOK.md` records why lint stays lax there. The `plan`
  header is the only thing that will ever tell you about a leftover numeric zero, for required and
  other fields alike (the latter as a softer `still carries the scaffold's numeric zero` note). A
  field `note:` does not silence it; `value: "0"` does.
- **A zero enum member is reported only when its NAME is a placeholder** — `*_UNSPECIFIED`,
  `*_UNKNOWN`, `*_NONE`, `*_INVALID`, `*_UNSET`, `*_UNDEFINED`. proto3 requires a zero member; it
  does not require that member to mean "unset". `enum Side { BUY = 0; SELL = 1; }` sending `BUY` is
  a deliberate value, and telling its author to "fill" it would be telling them to change the case
  they are testing.

## 13. A failure probe that lint demands you fill in

**Symptom.** A step that deliberately sends an incomplete body, to prove the server refuses it,
collects one `... is required by the contract ... while expecting success` error per required
field. The obvious response — fill them — destroys the probe.

**Cause.** The required-field rule skips a step only when `stepExpectsSuccess` says the step wants
a refusal, and that function looks at exactly two things: an expectation on the envelope path
(`conventions.envelope_path`, default `error.code`) with `not_equal: <envelope_ok>` or a string
`equals:` naming anything else, or one on `transport.code` / `transport.http_status` that names a
refusal (`contract/chainbodies.go`).
`allow_fail: true` does **not** count, and neither does asserting `error.details.0.app_code` —
which is the natural way to write a probe, and is how this was found: the skeleton in `PLAYBOOK.md`
§5 was written without it and produced 8 spurious errors on its own self-test.

**Fix.** State the refusal on the envelope path (`conventions.envelope_path`, default `error.code`)
as well as the app code. Both lines earn their place: the envelope path is what the lint reads, the
app code is what makes the receipt mean something.

# Green things that are not evidence

The entries above are ways to be wrong that eventually go red. §14 to §17 pass **every** check —
`lint ok`, a green `DRY-RUN OK`, a green run record — and still assert nothing. They are the reason this
document exists, so they get their own heading. Entries found later were added after them.

## 14. Two rules on one expectation: the second replaces the first

```yaml
- path: total_cost_base
  equals: ${steps.before.response.total_cost_base}   # the invariant you came to assert
  not_empty: true                                    # and this is the only one that runs
```

`Evaluate` is a fixed-precedence switch — `exists` > `not_empty` > `contains` > `not_equal` >
`equals` — so a second rule does not add a check, it **replaces** the one you meant. The precedence
runs weakest-first, so the entry passes. The natural way to say "present, and unchanged" is exactly
the way that drops the "unchanged".

`shrt chain lint` rejects it as of 2026-09-11, naming both rules and which one would have won
(`lintExpectRules` in `chain/lint.go`), and `GRAMMAR.md` §1's last table row is generated by
running the case. **Write one rule per entry and repeat the path** — two entries both fire.

## 15. A `${...}` inside a `vars:` value is a string, not a reference

```yaml
vars:
    shared_key: ${uuid}        # both steps should share one idempotency key
```

They share it, in the worst way: the scope is built by `mergeVars` (`runner/runner.go`) with no
resolution pass, so the literal seven characters `${uuid}` are sent to the server. Same reference in
a `body` is loud — status `error`, "unresolved reference". In `vars` it was neither resolved nor
reported.

`lint` rejects it as of 2026-09-11 (`lintVars`). The correct habits are unchanged: put `${uuid}`
directly in the body that needs it, or supply the value with `-var key=...` at run time.

## 16. A green `-dry-run` has only really checked step 1

Dry run resolves and validates, but there are no responses to resolve from, so every cross-step
reference resolves against a scaffold of the response message: `""` for a string, `"0"` for an
int64, `0`, `false`, the first enum member. A step whose body is `{ids: ["${create.id}"]}` dry-runs
as `{ids: [""]}` — a value the server rejects — and the dry run prints
`DRY-RUN OK (resolved and validated, nothing sent)`, with every step recorded as `skipped`. Dry run proves the chain's **shape**, and proves the first step's body. It cannot prove
any body downstream of a reference.

The other way round holds since 2026-09-24: a body `-dry-run` rejects in any step (an unknown field,
an invalid enum) makes `shrt run` refuse the chain with exit 1 before step 1 is sent, instead of
sending step 1 and erroring at step 2. A body rejected only through a scaffold value is not refused.

## 17. A step that only asserts `error.code == OK`

The oldest one, and still the most common: it asserts the server did not crash. Before references
were allowed in comparison values, **48.7% of steps in this corpus asserted only the error
envelope**, because that was the only thing an assertion could reach (`chain/expect.go`). It
is no longer the only thing, and the share has barely moved: **817 of 1887 steps, 43.3%, on
2026-09-12**. Neither number is worth quoting a day later. Re-derive — a step counts when every one
of its expectations names a path under the envelope field, the first segment of
`conventions.envelope_path` (`error` by default, `status` for `status.code`). Run it from the
directory holding `.shrt/`; it reads the envelope path and `paths.chains` from `.shrt/config.yaml`:

```bash
python3 -c 'import yaml,glob; c=yaml.safe_load(open(".shrt/config.yaml")) or {}; f=((c.get("conventions") or {}).get("envelope_path") or "error.code").split(".")[0]; d=(c.get("paths") or {}).get("chains") or ".shrt/chains"; st=[s for p in glob.glob(d+"/*.yaml") for s in ((yaml.safe_load(open(p)) or {}).get("steps") or [])]; e=[s for s in st if (s.get("expect") or []) and all(str(x.get("path","")).split(".")[0]==f for x in s["expect"])]; print(len(e), "of", len(st))'
```

What to write instead is `PLAYBOOK.md` §4.

## 18. A perfect contract-quality score, on a contract nobody wrote

**Symptom.** `shrt contract lint` says `0 error(s)`, `shrt contract quality` says `total score 0`,
and the gate says `at the baseline` — on an overlay that is nothing but scaffold. Measured
2026-09-12: delete `.shrt/contracts/pricing.yaml`, run `shrt contract init pricing`, and the 197-line
result with 40 literal `TODO` markers and zero curation passes all three.

**Cause.** Every term of the score asked whether something *declared* was vague — undocumented
request fields, failures with no `when:`, a missing `summary` (which counted as a gap but weighed 0).
Not one term asked whether anything had been declared at all, so **omission scored better than
partial work** and the floor was reachable by writing nothing. The `TODO` markers were found — lint
reports all 40 — but as WARN, and lint exits 0 on warnings, so nothing gated on them.

The cost was not hypothetical. Three agents re-authored `pricing.yaml` from scratch using only this
framework's own documentation; all three reached `lint ok` + `quality 0` + `0 undeclared codes` and
stopped, because the tool told them they were done. Against the real contract, `shrt contract plan`
composed the correct dependency order for **4 of 10** rpcs from the first author's overlay and **6 of
10** from the third's; the third's `needs:` recall was **1 of 6**. The missing `needs:`/`from:` edges
are the entire reason `plan` exists. Two of the three authors reported the hole themselves: *"the two
automated gates are satisfiable without doing any of the actual curation work."*

**Fix.** The score now charges for omission too — a write rpc with no `failures:`, an id with no
`from`/`same_as`/`value`, a response field in no `exports:`/`terminal:`/`soft_signals:`, an id wired
with no `checked_by:`, and a missing `summary` at weight 2 instead of 0. An unfilled `TODO` is not
charged as such: a `TODO` note or summary counts as saying nothing, and that is how it costs points. Same three
files, re-measured: the real contract **0**, the two blind overlays **4** and **1**, the bare
scaffold **56**. The development repo's `scripts/contract-quality.py` also exits 2 instead of 0 when it walks zero Go files
or finds zero `errmsg.New` sites — run from a copy outside the backend it used to report `0
undeclared` and pass, verifying nothing. Weights and exemptions: `PLAYBOOK.md` §7;
`contract/quality_test.go` pins each term.

The habit that outlives the fix: **a gate you can satisfy by deleting the file is measuring the
wrong thing.** Before trusting one, feed it an empty scaffold and check that it goes red.

## 19. The fixed score still passed three contracts that could not compose a chain

**Symptom.** §18's fix landed, and the experiment was re-run against it: three sonnet agents
re-authored `.shrt/contracts/pricing.yaml` from scratch in isolated sandboxes, using only this
framework's documentation. All three reached `lint ok`, `quality -domain pricing` **total score 0**,
`contract-quality.py` **0 undeclared codes** — and stopped. Scored against the real contract:

| | plan orders correct | quality | `needs:` recall | `required` recall | `before:` written |
|---|---|---|---|---|---|
| author 1 | 4/10 | 0 | 0/6 | 18/18 | 0 |
| author 2 | 4/10 | 0 | 0/6 | 18/18 | 0 |
| author 3 | 5/10 | 0 | 1/6 | 18/18 | 0 |

`required` recall was PERFECT and `needs:` recall was essentially ZERO, which is the whole finding:
the thing the gates can check got done completely, and the thing they cannot check got skipped
completely. Role recall told the same story a second time — 26/29, 20/29, 29/29 — at a score of 0,
because nothing charged for `requires_role:` either.

**Cause.** Every term still asked about something *declared*. `needs:` and `requires_role:` are
declarations with no descriptor counterpart, so their absence was free. `needs:` is what makes
`plan` compose a chain; `requires_role:` is what makes `plan` warn before a caller meets 1603.

**Fix, and what was measured before choosing it.** Two new weight-2 terms:

- **a READ rpc no write rpc can reach** — satisfied by `needs:`, by a `from`/`same_as` on any field
  (aliases included), or by a `before:` some write declares at it, i.e. by any edge `plan` walks
  that ends at a write. It fires when `plan <read>` would emit a one-step chain. Since then a
  `no_producer:` saying why also spares it. Fires on **0 of the corpus's 49
  read rpcs** and on r2-cand1 and r2-cand3 (4 points each); r2-cand2 stays 0.
- **an rpc with no `requires_role:`** — spared by the literal `NONE`, alone, which is how an rpc
  declares it reaches no role gate. Fired on **12 of 124**; 4 were verified real omissions against
  `db/migration/` (`000047`, `000195`, `000042`) and 8 were the partner-token surface plus staff
  `Login`, now carrying `NONE`.

The obvious stronger rule was **measured and rejected**: "every read must declare `needs:`" fires on
18 of 49 reads in the real corpus, and all 18 already compose correctly through a `from:` edge — 18
fires, 18 false positives. So was a **noun-pairing** signal (a `FetchX` whose `needs:` omits a write
`VerbX`): 24 fires on ground truth, 24 false positives — `FetchDeal` does not need `CancelDeal`,
`FetchAsset` does not need `UpdateAsset` — while recovering only 2 of pricing's 6 real edges.

**Say plainly what the fix does not do.** It separates **two of the three** authors from ground
truth. Author 2 wired an id on every read, so every read had *a* producer — the wrong ones. No term
can see an incomplete `needs:`, because the descriptor holds nothing to compare it against. The
blind spot is now documented in `PLAYBOOK.md` §7 rather than papered over;
the step-3 procedure gained the cheap detector that does work — run `plan` on every read and ask
whether that order could have produced a row for the read to find.

Two smaller things the same three authors found, both confirmed: `shrt contract init` used to write
`note: filter, empty means no filter` on every field of a read rpc, wrong for **18 of 184** such
fields in the corpus and for **6 of pricing's 12** — and, worse, a non-`TODO` note made the score
treat the field as answered. It now asks the question instead of answering it, which is also why the
bare pricing scaffold went from 56 to **112**. And a domain is, on that backend, the SECOND dotted
segment of the service name (`PLAYBOOK.md` §7 has the exact rule), so `acme.admin.pricing.…/FreezeAssetDailyMark` lives in `admin.yaml`, not in
`pricing.yaml`; `catalog ls -filter pricing` returns 11 while `contract init pricing` scaffolds 10,
and nothing said so.

The habit: **when a gate says done, ask which of the author's decisions it never looked at.** Here
it was every decision that had no counterpart in the machine-readable input — and those are exactly
the decisions the tool exists to capture.

## 20. A `before:` edge still pointing at an rpc that was retired

**Symptom.** Every gate is green and the composed order is still wrong — not missing a producer, but
sequencing it into a call that can no longer succeed.

**Cause.** `before:` names its target by procedure string. Nothing checks that the target still does
anything. Measured 2026-09-12: `position.yaml` ordered `SetInstrumentOpeningBalance` before
`SettlementSheetActionService/ConfirmSettlementSheet`, whose workflow is

```go
func (w *SettlementSheetWorkflow) ConfirmSettlementSheet(
	_ context.Context, _ uuid.UUID, _, _ string,
) (int32, error) {
	return 0, errmsg.AsError(errSheetConfirmRequiresApproval())
}
```

— every argument discarded, 1140 always. The live path became `ProposeSheetConfirmation` then
`ApproveSheetConfirmation`, and it is `ApproveSheetConfirmation` that declares **1118
SheetLineInsufficientChannelBalance** (`checkChannelCeilings`), i.e. the call that actually needs the
opening balance. So the edge pointed the prerequisite at the one rpc that could never consume it,
and `shrt contract plan ApproveSheetConfirmation` composed a chain that would hit 1118.

**How it was found, which is the point.** No gate found it. Two blind contract authors did, working
from the backend source, and a third flagged the target as dead independently. `lint` cannot see it —
the string resolves. `quality` cannot see it — the edge is declared. Retargeted to
`ApproveSheetConfirmation`; the approve chain now carries `SetInstrumentOpeningBalance` and the
retired rpc's own chain no longer does.

**The habit:** when an rpc's summary says it now refuses unconditionally, `grep` the overlays for its
procedure string before moving on. A retirement is not finished until the edges pointing INTO it are
re-pointed, and the only thing that will remind you is a reader.

## 21. A scaffolded body carrying every member of a `oneof`

**Symptom.** You follow `README.md` rule 3 — never hand-write a body from memory — paste what
`shrt contract show` or `shrt chain new` handed you, and shrt's own linter rejects it:

```
ERROR  [place_order] request does not match inv.v1.OrderRequest: proto: (line 1:16):
       error parsing "card_token", oneof inv.v1.OrderRequest.payment is already set
```

**Cause.** The scaffold walked `md.Fields()` and wrote one key per field. For a mutual-exclusion
group that is invalid by construction: `card_token: ""` and `bank_ref: ""` in one body arm the
group twice, and protojson refuses the second. The REQUEST listing made it worse by printing the
members flat, so nothing on screen said they were alternatives — the scaffold, which is the
authority an agent is told to trust, was the only thing an agent could read, and it was wrong.

**Fix.** `catalog.Scaffold` now emits at most ONE member of each group, the first in declaration
order, and the schema listing marks every member with its group and the full member list. A proto3
`optional` field is a SYNTHETIC group and is deliberately untouched — suppressing it would delete a
real field. When a curated contract arms one member (a `value`, `from` or `same_as` on a field that
declares a group), `shrt contract show` and `shrt chain new` scaffold that member instead of the
first. Pinned by `TestScaffoldEmitsOneMemberOfEachOneof`,
`TestScaffoldHonoursAPreferredOneofMember` and `TestSchemaMarksOneofMembersAndWellKnownForms` in
`catalog`.

## 22. A well-known type scaffolded as its seconds-and-nanos fields

**Symptom.** The same paste, the same linter, a different refusal:

```
ERROR  [place_order_2] request does not match inv.v1.OrderRequest:
       proto: syntax error (line 1:11): unexpected token {
```

for a body that reads `due_at: {seconds: "0", nanos: 0}` — which is exactly what the message
`google.protobuf.Timestamp` contains.

**Cause.** protojson gives the well-known types a JSON mapping that is NOT their field layout: a
Timestamp is an RFC3339 string, a Duration is `"3.5s"`, a FieldMask is comma-joined lowerCamelCase
paths, the wrappers are bare scalars (`Int64Value` a string number), `Empty` and `Struct` are `{}`.
The scaffold expanded them like ordinary messages, so every one of them produced a body the server
could never parse.

**Fix.** Measured, not reasoned: the placeholder for a well-known type is protojson's own marshal of
that type's ZERO message (`catalog/wellknown.go`), so it round-trips by construction. The table
there only decides which types are well known and carries the accepted form the schema listing
prints; a type missing from it is scaffolded as an ordinary message. `google.protobuf.Value` is the single type that cannot be
marshalled at zero — a Value with no kind set is not a value — and it scaffolds as `null`, which
protojson accepts. `google.protobuf.Any` scaffolds as `{}`, which is accepted as an EMPTY Any;
anything else in it needs a `@type`, and the schema listing says so, next to the field, along with
the accepted form of every other well-known type.

**The same mapping bites one edit later, and that half was missed first time round.** Lint validates
a body with every `${...}` replaced by a stand-in of the right shape, because the real value does not
exist until run time. That stand-in was `{}` for anything message-kind — so `due_at: ${vars.when}`,
the single likeliest edit an author makes after pasting a scaffold, was rejected with the *same*
`unexpected token {` as the bug above, on a chain that was completely correct. The fix is one branch:
a field that has a JSON form stands in as an example of THAT form (`"1970-01-01T00:00:00Z"`, `"0s"`,
`"0"`, `false`, `0`), carried on the field by the same code that computes the scaffold, so the two can
never disagree. A plain message field still stands in as `{}`, which is what it should be, and a wrong
LITERAL in a well-known field is still rejected — the loosening is only for the case where no value is
present to judge. `TestAReferenceStandingInAWellKnownFieldLintsClean` and
`TestPlaceholderMatchesTheJSONFormOfTheFieldItStandsIn` pin both halves.

## 23. A streaming rpc that scaffolds, lints, and then fails at the transport

**Symptom.** `shrt catalog ls` lists `WatchOrder` exactly like a unary rpc, `shrt chain new` writes
a step for it, `shrt chain lint` says `ok`, and the runner POSTs it as a unary Connect call. What
comes back is a parse failure with nothing in it about streaming.

**Cause.** Nothing read the descriptor's streaming flags — `grep -rn Streaming` across shrt's own source returned
nothing at all. shrt's transport is unary by design: one POST of JSON to `/pkg.Service/Method`, one
response body (`transport/client.go`). A rpc that answers with a stream is out of scope, and
the tool had no way to say so.

**Fix.** `catalog.Method` carries `ClientStreaming` / `ServerStreaming` from the descriptor.
`shrt catalog ls` and `shrt catalog describe` mark such an rpc, `shrt contract show` prints a
`STREAMING` line, `shrt chain new` refuses to scaffold one, `shrt chain lint` reports a step
that calls one as an ERROR, and `shrt run` and `-dry-run` refuse the whole chain before anything is sent,
exit 1 with no run record, like any other static refusal (until 2026-09-24 they did not: dry-run
printed `DRY-RUN OK` and a run sent it; after that, the step was recorded ERROR, exit 3, with a run
record saved, and earlier steps had already been sent). `shrt contract plan` refuses a streaming target, and any plan whose graph pulls one in, with the same sentence (it used to write a chain that could never lint), and `contract status` never counts one as REACHED. `describe`, `chain new` and `chain lint` carry the same sentence, which
names the rpc, the kind of streaming, and the unary shape that cannot carry it; `catalog ls` and
`contract show` print a shorter `OUT OF SCOPE` marker. An adopting repo with streaming methods
learns they are out of scope from the tool, not from a confusing runtime parse failure.
`TestStreamingFlagsRideOnTheMethod`, `TestLintErrorsOnAStepCallingAStreamingRPC` and
`TestAStreamingRPCIsRefusedBeforeSendingInRunAndDryRun` pin it.

**All three shared one absence, and that is the part worth keeping.** Nothing checked that a
scaffolded body validates against the message it was scaffolded FROM — a property the tool can test
against itself, with no server involved. It is now two tests:
`TestScaffoldedBodyValidatesForEveryRPCInTheCorpus` walks every rpc in the development repo's real
descriptor (in the module it skips, because there is no `.shrt/descriptor.binpb` for it to find),
and `TestScaffoldedBodyValidatesForEveryRPCInTheRichFixture` walks a fixture built for the proto
features the real surface happens not to use (`catalog/catalogtest/rich.go`: a three-armed group and
a two-armed one, twelve well-known types, a repeated message, a map, an enum, a proto3 `optional`, and the three
streaming shapes). The corpus test is the one that would have caught all three the day a new proto
feature reached the surface; the fixture is the one that catches them today, because the surface
this grew up against uses none of those features.

## 24. A read step that passed, and the response was empty

**Symptom.** A read step (an rpc whose name starts with a prefix in
`conventions.read_only_prefixes`; default list in `GRAMMAR.md`) asserts `error.code == OK`, passes, and
the body is `{"rows": []}`. The step is green, the chain is green, the sweep is green — and the step
proved the opposite of what its author meant: the server answered, and there was nothing there.
This is the operational shape of §19's blind spot, a chain that creates the entity but never fires
the event that writes the row being read. Four independent contract authors have hit it, and the
corpus has it too.

**Cause.** §17 says a step asserting only the envelope asserts that nothing crashed. Nothing looked
at whether the response carried anything, because the assertion could not: there was nothing in the
chain file to compare against.

**Fix.** `shrt chain hollow` reads the run records rather than the chain files, which is what makes
the emptiness visible at all. Measured 2026-09-12 over 2438 local records: 9112 passed read steps,
1965 asserting only the envelope, 529 of those hollow, across 34 distinct (chain, step) pairs. 28
are refusal probes where an empty body IS the pass and now carry their reason in
`.shrt/hollow-allow.txt` (since 2026-09-24 a probe that pins its non-OK envelope value is recognised
without an allowlist line, as is `<list>.0 exists: false`; the chain-side check resolves a
`${vars.x}` pin from the chain's `vars`, and treats any other reference on the envelope as
envelope-only, so `status.code equals: ${vars.ok}` no longer passes for a refusal probe); 1 has since gained a data assertion in its chain; 5 remain, four of them in
`readonly-fetch-sweep` — a sweep of reads with nothing in the chain that creates the data.

Two things that reading the numbers wrong will cost you. **A proto3 JSON int64 arrives as a STRING**,
so a body of `{"opening":"0","closing":"0","line":[]}` is a read that found nothing, not a statement
that summed to zero; treating `"0"` as a number is 80 of those 529, and 6 of the 34 pairs. And **the
allowlist is not inferrable from step names**: matching `reject_` and `malformed_` finds the
candidates and would silently exempt every future step whose name happens to contain the substring,
including a real regression. The reason field is the whole file; an entry without one is refused.

## 25. A gate that skipped its own comparison because the file was not there

This entry is about the development repo's own gate script, `scripts/check.sh`, and the scripts and
tests it names. None of them ships in the shrt module; the lesson is the part that transfers.

**Symptom.** `check.sh` printed the agent-kit section and moved on, every run, with
`.claude/skills/shrt/SKILL.md` deleted. Measured 2026-09-12: the loop guarded its `diff` with
`[ -f "$dst" ]`, so an absent destination was not a drift — it was nothing to compare, and nothing
to compare read as agreement.

**Cause.** Third instance of §18 in this repo, and the first one inside `check.sh` itself. The guard
was defensive about a file that might not exist yet; the effect was that deleting the file satisfied
the gate that exists to protect it.

**Fix.** `scripts/check-agentkit-sync.sh` fails when either side is missing and says which. More
usefully, `internal/guard/blindgates_test.go` now enumerates every gate by READING `scripts/check.sh`
and, for each, removes or empties that gate's input and asserts a non-zero exit. A gate added to
`check.sh` and not covered there fails the test by name. Running it the first time found three
greens-while-blind, all now red: this one, `shrt contract lint` on a library with no overlays, and
`shrt chain lint` with no chains. One gate stays green while blind with its reason recorded in the
test — `go build ./...` exits 0 on a module with no packages, and `go vet ./...` in the same section
exits 1 on that same input.

**The same defect was in the detector, one level up, and this is the more valuable half.** The
scanner recognised a gate by prefix — `./shrt `, `python3 `, `bash `, `go `, `gofmt ` — and its
default for anything else was *skip in silence*. So the two inline `diff` loops were not green while
blind, they were INVISIBLE, and so was every gate anyone might write as `grep -q … || exit 1`, as a
bare script path, or inside an `if`. The test went on reporting full coverage of a shorter list than
`check.sh` actually ran. A detector whose default is "not a gate" fails exactly the way the gates it
watches do: it reports green about a question it never asked.

**The default is now inverted.** Every line of `check.sh` is split on unquoted `&&`, `||`, `|` and
`;`, stripped of `if`/`then`/`case`-label syntax, and must end up as one of three things: a gate with
a probe, an entry in the small `nonGates` table that carries the one-line reason it cannot go blind
(`echo` prints, `exit` propagates a verdict, `[ … ]` inspects state, …), or punctuation carrying no
command. Anything else fails by section and line number with the two remedies spelled out. That
accounting is a test inside the development repo, not something to run in yours — the transferable
part is the shape: a gate list whose default is to REFUSE a line it cannot classify. The reason table is the same shape as the backend's
`requiretx_exemption_gate_test.go` — an exemption must carry its premise, or it exempts something
nobody examined.

The consequence for `check.sh` is unchanged and now enforced rather than hoped for: a section whose
work is an inline `for` loop over `diff` cannot be probed, so it must become a named script. That is
why the `.shrt/docs/` drift check is `scripts/check-docs-sync.sh` in its own section rather than a
second loop under the agent-kit one.

## 26. `exists: true` on a field the server never sent

**Symptom.** A step asserts that a login returned a token. It passes. The login was refused and the
response body had one key in it.

**Cause.** Every response is re-encoded through `protojson` with `EmitUnpopulated: true` before any
expectation runs — that is what gives a run record a stable shape for the differ to compare across
runs. By the time `exists` looks, `token: ""` and `expires_at: "0"` are sitting in the body that
the server never put them in. So `exists: true` could not fail and `exists: false` could not pass,
for every scalar of a message the descriptor knows. Neither lint nor `-dry-run` could see it: the
path is a real field, the rule is a real rule, and the verdict was green.

Three chains in this corpus leaned on it, written by three authors who each measured the wire by
hand, found the field there, and wrote `exists: true` believing it pinned what they had just seen.
It never did — an expectation cannot reach wire bytes, because the re-encode happens first.

**Fix.** Fixed 2026-09-22: `CanonicalizeWithPresence` returns the message a second time with
unpopulated fields left out, and `exists` reads that. What remains true, and is not a bug: **a proto3 scalar without
`optional` has no presence on the wire at all.** `false`, `0`, `""` and a zero-length list are
encoded identically to a field that was never set, so no tool can tell you which happened. If that
distinction is what you need, the proto must say `optional`. Otherwise assert the value
(`equals: false`) or the emptiness (`rows.0 exists: false`), which are things the wire can answer.
The second table in `GRAMMAR.md` §1 is generated by running the rules against a body with one key.

## 27. A CI gate of `lint && run`, green on a chain that proves nothing

**Symptom.** The obvious gate is wired up, every chain is green, and a step asserts nothing at all.

**Cause.** `shrt chain lint` reports the assertion-quality findings — a step with no `expect`, an
assertion that cannot fail — as **warnings**, and exits 0. (An `expect` path the response message
has no field for is an error since 2026-09-24, §36.) That
default is right while you are authoring, when the chain is half-written by definition. It is wrong
for a gate, and the gate is what a team copies out of the docs.

**Fix.** `shrt chain lint -strict` promotes the assertion-quality warnings to errors and exits
non-zero: an assertion that cannot fail (the kinds still reported as warnings, such as an enum
comparison every value satisfies), a step asserting nothing, a reference nothing can produce,
and an `allow_fail` on a step with expectations, where it does nothing. An expect path that can
never match is not on that list because it needs no promoting: it is an error with or without
`-strict` (§36), and so are `exists: false` on a path the message has no field for and an export
reading a field the response does not have (the run fails that step). It has
existed since the flag was added, but no document mentioned it, so an adopter reading the four docs
end to end would not learn it was there — one did not, and wired up the weak gate. The development
repo's `scripts/check.sh` runs the strict form. Since 2026-09-22 the non-strict run also prints, after the warnings, that
`-strict` is what a gate should run.

## 28. A cached token the backend has forgotten, re-sent forever

**Symptom.** Every step of every chain fails on `path not present in response`, as though the
backend had stopped returning any data. `shrt doctor` says `0 expired`. `rm .shrt/tokens.json` fixes
it, and nothing told you to.

**Cause.** Two faults, and the first hid the second.

`Invalidate()` cleared the token in memory and left it in `.shrt/tokens.json`, so the very next
`Token()` read the same dead credential back off disk and the retry re-sent it. That applies to
**every** unauthenticated response, including a plain HTTP 401 — this repo never noticed only
because on the backend this kit was first written for, a token is dead in practice only when it has expired, and expiry is caught before the
call goes out.

Under that, the retry never fired at all for a deployment that answers **HTTP 200 with the refusal
in its envelope** — the shape `conventions.envelope_path` exists to describe. `Result.Error` is
only populated for a non-200 status, so an in-band `unauthenticated` was invisible to the auth
middleware, and what the chain saw instead was every assertion failing on a body that carried a
verdict and no data.

**Fix.** Both, 2026-09-22: `Invalidate()` drops this profile's entry from the cache file as well as
from memory, leaving other profiles' entries alone, and the middleware reads the configured
envelope path on a 200 body. A dead token now costs one extra login instead of a red corpus. What
`doctor` still cannot tell you is whether a cached token is live — only the backend knows that, so
its line says so rather than implying `0 expired` means healthy.

**Changed 2026-09-24:** the re-send is now for reads only. A backend that performs a write and then
answers 401 had it performed twice, and the step record did not say the call went out twice. A call
answered unauthenticated still drops the token; a read (`conventions.read_only_prefixes`) is re-sent
after a fresh login and records `auth_retry: resent`, and a write is not re-sent: its step fails with
`auth_retry: not_resent` and a warning, and the next run logs in fresh. A dead cached token therefore
costs one red write step, not a doubled write.

**Also 2026-09-24:** Go's HTTP client silently re-sent a POST carrying an `Idempotency-Key` or
`X-Idempotency-Key` header when a reused connection dropped after the request went out, so a step
whose connection closed mid-flight passed with the write performed twice and nothing recorded. shrt
now never lets the transport re-send a request whose body was sent: such a drop is a step `error`
saying whether the call took effect is unknown. A request that provably never left (nothing written
on a stale idle connection) is still retried on a fresh connection.

## 29. `validate_output` reporting the one status that means "nothing was sent"

**Symptom.** You turn on `conventions.validate_output`, a response fails to match its proto message,
and the run says `error` — the status GRAMMAR §8 and PITFALLS §4 both define as *no request was
sent*, and as evidence about your fixture rather than the backend. The request was sent. The backend
answered 200.

**Cause.** The branch reused the generic `fail()` helper, which sets `error`. So the single status
the documented remedy for descriptor skew can produce was the one status whose documented meaning
excludes it.

**Fix.** 2026-09-22: the step is `failed` and carries `"drift": true`. `failed` because the request
was sent; `drift` because no expectation was evaluated, so nothing in the step is evidence about the
rpc — the body the assertions would read could not be decoded. `allow_fail` does not swallow it:
a refusal is not what happened, and swallowing it would hide the only thing `validate_output` was
turned on to find. Run `shrt catalog build` and re-run before reading it as a backend defect.

## 30. A path copied out of `contract show` that can never match

**Symptom.** You paste `status.details.error_code` from EXPORTABLE PATHS into an `expect:`. Lint says
`ok`. `-dry-run` says nothing. The run fails with `got=<nil> (path not present in response)`.

**Cause.** `details` is a repeated field, so the runtime path needs an element:
`status.details.0.error_code`. The hint walker descended into repeated messages without an index,
and lint's "path can never match" check resolved field names one at a time and never asked whether a
list had been crossed — `FieldAt` skips index segments and so never noticed a missing one. Every
check upstream of live traffic agreed the path was fine.

**Fix.** 2026-09-22: the walker emits the indexed form and marks repeated leaves as `repeated <kind>`;
lint reports the un-indexed form and names the path that works. Since 2026-09-24 it is an error
without `-strict`, and so is `exists: false` on such a path, which is never present and so cannot fail.

## 31. A lint warning that cost the contract its detail

**Symptom.** One backend code is raised for three different fields, with three different `field:`
values and three different `when:` prose. Declaring all three gets
`failure 2 repeats 1105 MissingField already listed as failure 1`, and the obvious way to silence it
is to merge them into one entry — throwing away the only thing that told the branches apart.

**Cause.** The duplicate key was code + reason. `field:` is exactly what distinguishes two branches
sharing a code, and it was not in the key. A blind adopter merged two `1204` branches to make the
warning go away, which is the tool talking a contract author out of the detail the contract exists
to hold.

**Fix.** 2026-09-22: the key includes `field:`. Two entries differing only in `field:` are two
branches and are not reported; the same branch written twice still is, and the warning now names the
field that collided so the author can see which it means.

## 32. A whole corpus asserting an envelope this backend does not have

**Symptom.** `shrt init` prints `17 of your 17 rpc(s) answer with a message carrying a field at "status.code"`
and asks you to paste a `conventions:` block. You are mid-adoption and do not. Nothing mentions it
again — `shrt doctor` reports every check ok — and every chain you write asserts `error.code`, a path
no response carries.

**Cause.** `init` detects the path from field NAMES and genuinely cannot write the block: it cannot
guess `envelope_ok`, because the success value is data rather than a name, and writing a path with
the wrong success value is worse than writing nothing. So it printed and moved on, and no later
command re-read the question.

**Fix.** 2026-09-22: `doctor` checks it every run. A configured `envelope_path` no response message
declares is an **error**. No `envelope_path` at all, while the responses agree on a different one, is
a warning naming the path it found.

The same check covers the one that fails silently. A wrong `envelope_path` is loud — every assertion
misses at once. A missing `item_envelope_path` is not: a batch rpc answers `OK` at the top level
while refusing every line, and a step asserting only the envelope passes having achieved nothing.
`doctor` now detects a per-item verdict nobody configured and says so.

2026-09-23: the detection read field NAMES, so on a backend whose list reads return rows with an enum
`status` it suggested `<rows>[].status`, a business field, and missed the batch rpc whose items
repeat the envelope message. Configuring the suggestion turned every list step red. It now suggests
only `<list>[].<envelope_path>` — the configured (or detected) envelope repeated inside a list
element — ranks first the element whose envelope field is the same message as the top-level one,
and never proposes a field just because it is named like a status. The finding says it is a guess:
verify it against one response you know refused an item before setting it.

## 33. A scaffold that ignores the contract you just wrote

**Symptom.** The domain has a curated contract. `shrt chain new` gives you three steps and
`shrt chain lint` answers with seven errors, on fields the contract already has a `value:` or a
`from:` for. You fill them in by hand, from the contract, by reading it.

**Cause.** `contract plan` applied the wiring; `chain new` and `contract show`'s CHAIN STEP did not.
Both went through a scaffolder that saw only the proto descriptor, so every field came out as its
zero value — including the ones whose answer was sitting in `.shrt/contracts/`.

**Fix.** 2026-09-22: both use the same contract-aware builder `plan` uses. `value:` is applied.
`from:` is resolved **between the steps you asked for** — `chain new a b` wires b's input to a's
output when the contract says so — and a producer that is not among them is reported by name on
stderr rather than left as a silent empty string (`contract show` since 2026-09-24; before that
its CHAIN STEP left the empty string without a word). The summary becomes the step description and the
contract's `exports:` are written out.

Measured on the backend this kit was first written for, `chain new` over CreateBook + CreateAsset + CreateDeal: 14 lint errors before, 10
after, and the 10 are fields whose producers genuinely are not in the list — each named in a note.

## 34. A backend error code no chain can ever reach

**Symptom.** The backend answers `internal` / a catch-all code for any handler exception, and curl
reaches it in one line:

```
$ curl ... -d '{"page":"not-an-object"}'
{"status": {"code": "internal", "details": [{"error_code": 1000, ...}]}}
```

`shrt` cannot: `ERROR request does not match ... proto: syntax error (line 1:9)`. Same for a code
that needs an enum value the descriptor does not know. Meanwhile the coverage term — codes the
backend raises that no contract declares — charges you for it.

**Cause.** Not a bug. Every request is validated against the descriptor before it is sent; that is
the property the whole tool rests on. A refusal reachable only by a body the proto cannot express is
out of reach for any descriptor-driven client, permanently.

**Fix.** Declare it with `unreachable:` and the reason. It stays documented, stays out of the
coverage denominator, and the next reader does not spend an afternoon trying to write the chain.
`GRAMMAR.md`'s `unreachable` entry says so as of 2026-09-22; before that nothing named this boundary
and a blind adopter had to derive it and invent the remedy.

## 35. Run records of a chain you deleted, still in the totals

**Symptom.** `shrt chain hollow` reports N records; you deleted six chains last month and their run
directories are still there, feeding a ratcheted count.

**Cause.** Deleting `.shrt/chains/<name>.yaml` does not touch `.shrt/runs/<name>/`, deliberately —
a run record is evidence of what the backend did, and the chain going away does not unmake it.
Nothing said so, and nothing separated them.

**Fix.** 2026-09-22: `hollow` compares the run directories against the chains that exist. Records
with no chain are excluded from the counts and from the gate — a finding naming a chain that is gone
cannot be acted on — and the directories are listed by name so you can delete them when the evidence
has served its purpose. They are still not deleted for you. Measured on this repo at the change: 18
records under 6 directories, contributing 0 findings, so the ratchet held at 31.

## 36. `exists: false` on a misspelt field, green on every run

**Symptom.** A step asserts `{path: thing_idd, exists: false}` on a response whose field is
`thing_id`. `lint -strict` says `ok`, and the step passes on every run.

**Cause.** lint checked `expect` paths against the descriptor for every rule except `exists: false`,
which it skipped as "absence is the point" — and the message for a bad path even suggested writing
`exists: false`. A field the message does not declare is absent from every response, so the
assertion could not fail.

**Fix.** 2026-09-24: an `expect` path the response message cannot carry is a lint **error** for every
rule; with `exists: false` it is reported as an assertion that cannot fail. `exists: false` on a field
the message declares is still the way to assert absence. If the field is genuinely new, the
descriptor is stale: `shrt catalog build`.

## 37. A refused call, green because its data assertion read the zero value

**Symptom.** `AddStock` with `qty: 0` is answered `status.code: REJECTED` (`InvalidQty`). The step
asserts only `qty_on_hand equals: 0` and is `ok`, with no warning.

**Cause.** A refusal leaves every data field at its zero value, so an assertion that the value is
zero holds on the refusal. Nothing on the step said the call had to succeed or had to be refused.

**Fix.** 2026-09-24: a step that declares expectations, is refused in-band, and has none pinning the
verdict (`equals` on the envelope, or a rule on the envelope or a `transport.*` path that would fail
on a successful answer) is `failed`,
with an `envelope` entry naming the refusal. Assert `status.code equals: SUCCESS` on a call that must
succeed, or the refusal code on one that must be refused.

The same hole was open through a response with no verdict at all: `{}` or `status: {}` has
`status.code == ""`, which is not a refusal code, so `qty_on_hand equals: ""` passed on it. Since
2026-09-24 an absent or empty verdict, on an rpc whose response message declares the envelope
path, is treated like a refusal: the step fails with an `envelope` entry saying no verdict was
sent, unless an expectation pins the envelope (`exists: false` included) or the transport.

And through a pin the refusal itself satisfies: `status.code not_equal: ""`, or `not_equal: REJECTD`
with a typo, holds on `REJECTED` exactly as on `SUCCESS`, so it declares nothing, yet it used to
count as pinning the verdict and turned the refused step green. Since 2026-09-24 a pin counts only
if it is an `equals` on the envelope or would fail on the ok value (`not_equal: SUCCESS`,
`contains: REJ`, `exists: false`, `transport.code equals: unauthenticated`), after resolving its
references; the same rule already held for a batch line's verdict. `chain lint` warns
(`unfailable-assertion`, failed by `-strict`) on `not_equal: ""` on the envelope; a misspelt code on
a string-typed envelope cannot be told from a real one statically, so only the runner catches it.

## 38. A password or a token in clear in a run record, though `redact` covers its field

**Symptom.** `**.*password` and `**.access_token` are redacted, yet the run record, the pending
proposal and the safe spot show the password and the live token: in a request built from
`${env.API_PASSWORD}` or `${tok}` (an export of `access_token`), in a response echoing them, and in an
expectation's `want`/`got`.

**Cause.** Redaction matched paths only. A secret copied into a field with an innocent name — a
customer `name`, a product id, a message — was not under any redacted path.

**Fix.** 2026-09-24: the runner also scrubs by value every value an auth body reads from `${env.*}`,
every token a login returned, and every value exported from a redacted path, wherever it appears in
the record; the report and safe spot are built from the record. A value shorter than 4 characters
is replaced only where it is the whole string, so a one-letter username does not shred the record.

Only secrets are scrubbed by value: an auth body value counts when its field is covered by `redact`
(the password), not a username or another login field no pattern covers. Before this, the username
`clerk` was scrubbed too, so a request `name: "clerk made"` was stored as `"<redacted> made"`. A safe
spot approved with such a mangled request shows it once as a request difference in `verify`.

A token a login step in the chain returned was scrubbed only when it seeded a profile or was
exported: read directly (`name: ${login_clerk.access_token}`) under a login body no profile has, it
stayed in clear. Every response of a login rpc now gives up its `token_path` value and every value
under a redacted path as secrets, whichever step called it.

Likewise an env credential a STEP body read (`password: ${env.CLERK_PW}` in an in-chain login) was
path-redacted in that step but stayed in clear wherever it was echoed. Every `${env.*}` value a step
body reads into a field covered by `redact` is now scrubbed by value in the whole record.

# Decisions, so they are not relitigated

**A `${...}` in `vars:` is rejected, not resolved** (2026-09-11). The tempting fix is to resolve var
values at scope-build time, which would make `vars: {shared_key: ${uuid}}` do what its author meant.
It was rejected: only generator references (`${uuid}`, `${now}`, `${nowunix}`) could ever resolve
there — a `${create_deal.id}` cannot, because no step has run — so the feature would have to teach a
second rule about *which* references work *where*, in a tool whose selling point is that a reference
either resolves or fails loudly. The use case is already served, correctly, by `-var key=value` at
run time, which is what the development repo's `scripts/verify-all-flows.sh` does for every chain it runs. A loud refusal
with two working alternatives beats a clever resolver with a new silent-failure surface.

**`GRAMMAR.md` owns every key table** (2026-09-11). In the development repo
`scripts/check-key-ownership.py` enforces it; nothing in the module does. `docs/chain-spec.md`,
`docs/contracts.md` and `agentkit/skill/SKILL.md` each used to carry their own copy. That is how `oneof` came to say "at most one" in one file and "exactly one" in another with
nothing to notice — 46 duplicated rows across three files at the time of the sweep. They now point
at the generated table. Prose, rationale and worked examples stay where they were; only the key
enumerations moved.
